# AGENTS.md

## architecture
atlas_prime v0.4.0 is a Termux/Android system-monitor daemon written in Rust
(edition 2024). It is a long-running background service: the OS starts it, it
samples hardware, writes to a local sqlite DB, and exposes a WebSocket + JSON API
over HTTP so a phone or laptop browser can render the dashboard.

The design is six domains in `src/v1/` (`src/v1/mod.rs`): `system` (hardware
collection), `task` (spec-driven child processes), `web` (ntex HTTP/JSON API +
dashboard), `db` (passive sqlite storage), `operator` (the only self-driving
module — periodic sampling), and `notify` (passive termux-notification outbound).
They share nothing beyond the standard path/triple — each domain does ONE job and
passes data downstream through public fns / db rows / HTTP routes. Never skip a
layer: e.g. let `web` read `db.history` or the operator's live cache; never read
sensors directly.

```
              OS (Termux, Android untrusted_app)
                     │  sensors, su, /proc, /sys, termux-api CLI
                     ▼
    operator  ──► system  ──► db      operator is the only self-driven module;
 (3 sampling        (8 domains)      db is passive (open/insert/history);
  loops, 120s)                        web reads db.history + operator live cache
                     ▲
                     │  GET /system/* , /system/cli/network , /system/cli/battery ,
                     │  /db/history , /task , POST /task/*
                     ▼
    task        notify
 (child procs)  (termux-notification, zero state)
   web  ──serve──► browser (dashboard.html, embedded in binary)
```

## commands
Build & run:
```
cargo build --release
cargo run --release
cargo test --release
```
Notes: release profile is optimized for size (opt-level=z, lto, strip,
panic=abort). First build pulls many crates (offline Termux mirror may be slow);
use `cargo build` (debug) during development, `cargo build --release` for deploy.

Logs:
- `~/.local/share/atlas_prime/atlas.log` — the daemon's runtime log (created on boot).
- `crash.log`, `a.log`, `boot.log` — in-repo operational history (gitignored).

Dashboard:
- Open `dashboard.html` in a browser, or hit the API base when the daemon runs
  (default `http://0.0.0.0:1025`, override with `ATLAS_BIND`). `dashboard.html`
  is embedded at compile time via `include_str!` (see `src/v1/web/mod.rs`) so
  edits to the **root** file take effect only on rebuild — **but** a copy placed
  at the data dir (`~/.local/share/atlas_prime/dashboard.html`) overrides the
  embedded one at runtime on every request (dev hot-reload).

## entry points
The daemon is fully background (no TUI, no foreground prompt). Startup order
(`src/main.rs`): (0) single-instance **flock** lock on
`~/.local/share/atlas_prime/atlas_prime.lock` — process exit (incl. crash/kill)
releases it, so a second launch just exits; (1) load task specs (`Task::update`,
autostart items pulled); (2) start `Operator::start()` (the only self-driven
module, 2-min round sampling, rolling 20000 rounds); (3) spawn web in a background
thread; (4) block on Ctrl+C; (5) on Ctrl+C: stop operator sampling, send stop to
all in-run tasks.

| What | Where | Notes |
| --- | --- | --- |
| process main / server boot | `src/main.rs` | `fn main()`: flock → task spec load → `Operator::start()` → `Web::spawn(bind)` → block on Ctrl+C. |
| operator sampling (3 loops) | `src/v1/operator/mod.rs` | `Operator::start()`, `Operator::stop()`, `Operator::sample_now()`, `run_sampler()`(120s) / `run_net_meter()`(1s) / `run_proc_meter()`(5s) run on one runtime, same stop wake. |
| db sink | `src/v1/db/mod.rs` | `Db::open()` (sqlite + `records` table), `Db::insert()` (single call site = operator), `Db::history()`. |
| web server | `src/v1/web/mod.rs` | `Web::spawn(bind: String)` threads an ntex System; `serve()` builds the router. |

### the data flow (how data moves)
```
operator  run_sampler   (120s)  system·{cpu,mem,disk,gpu,thermal,battery} → db.records (kind=system/…)
operator  run_net_meter  (1s)   system::network·{rx_bps,tx_bps} → db.records (kind=net)
operator  run_proc_meter (5s)   system·proc → live cache ONLY (never written to db)
web       browser ──GET──► web (routes) ──reads──► db.history / system live cache
task      main load specs → Task::spawn/run/stop → (stdout/stderr/exit captured) → /task
notify    policy event → termux-notification (passive, no state)
```
The operator loop is the single writer of sensor + net data to db. The db never
drives itself (passive `open`/`insert`/`history`). The web layer only READS (via
`db.history` or the operator's live cache) and serves it.

### the loop driver (operator)
`Operator::start()` runs **three loops** on the db's shared runtime:
1. `run_sampler` — every `SAMPLE_INTERVAL` = **120s**, collects every domain,
   writes system rows + the net row for that second.
2. `run_net_meter` — every `NET_SAMPLE_INTERVAL` = **1s**, per-netgroup rx/tx
   bps, writes `kind=net`.
3. `run_proc_meter` — every `PROC_SAMPLE_INTERVAL` = **5s**, refreshes the proc
   snapshot cache for `GET /system/proc` (no db write).

All three share one stop wake (`Operator::stop()`). Policy lives in the submodules:
`batterywatch` (battery low/battery thresholds — see NOTES) and `memwatch` (mem low).

### data model (Record — the db row shape)
Every db row is a normalized `Record` in the `records` table
`(ts TEXT, kind TEXT, key TEXT, value REAL)`:

| field | meaning |
| --- | --- |
| `ts` | RFC3339, second precision, UTC — written as-is into the `ts` column |
| `ts_secs` | Unix seconds (same instant as `ts`); web's `/db/history` projects it to `t` via `CAST(strftime('%s', ts) AS INTEGER)` |
| `kind` | discriminator for table/panel |
| `key` | sub-entity within a kind (core name, net-group name, gpu field) |
| `value` | the sample (`f64`) |

The `kind` string is the single source that decides both the trim scope and the
dashboard panel it renders. Rows accumulate in memory and flush to sqlite via a
mutex in one transaction; each round trims: `SCOPE_NET` (`kind='net'`) to
`NET_MAX_ROUNDS`, `SCOPE_OTHER` to `MAX_ROUNDS`.

| kind | key example | dashboard panel |
| --- | --- | --- |
| `system` | `cpu`, `mem`, `disk`, `thermal`, `battery`, `ip` | CPU / MEM / DISK / THERMAL / BATTERY / IP rings |
| `net` | `<group>.rx_bps` / `<group>.tx_bps` | Net rings + group list |
| `gpu` | `load_pct` / `freq_mhz` | GPU ring (lazy-seeded on first `/system/gpu`) |

`gpu.load_pct`/`freq_mhz` are `Some` only, 2 minutes/round; `proc` rows are
cache-only (no `kind` written).

## conventions
- **Six-domain zero-shared-data rule**: per `src/v1/mod.rs`, the domains share only
  the standard path triple (`PROJECT`); everything else is isolated. Respect it —
  no cross-domain shortcuts.
- **operator self-drives, db is passive**: operator is the only module that
  samples on a timer; db never initiates. New sensor paths funnel through the
  operator loop, never write `db` from `system` or `web`.
- **Normalized long-form rows**: one `Record` per `(kind, key, ts)`, `value` is
  scalar. Don't reshape `records` into wide columns; keep `value` an f64.
- **Batched db writes + rolling trim**: rows accumulate in memory, flush via mutex;
  each round trims net vs non-net independently. This trades write latency for
  throughput on constrained Termux storage — don't "fix" it to per-row without
  re-evaluating the cost.
- **Release profile is size-optimized**: `opt-level=z, lto, strip, panic=abort`.
  Debug builds (`cargo build`) are for iteration; `--release` for deploy.
- **`include_str!` dashboard**: `dashboard.html` is a single self-contained HTML
  file embedded at compile time (see NOTES). Keep it that way.
- **120s / 1s / 5s cadences**: sampler 120s, net 1s, proc 5s. Constants live in
  `operator/mod.rs` (`SAMPLE_INTERVAL`, `NET_SAMPLE_INTERVAL`, `PROC_SAMPLE_INTERVAL`).
- **CPU core count is dynamic** from present threads — don't hardcode core counts
  in `system/cpu.rs`; the collector reads what is present.

## NOTES
Act-on items for the user (these are the non-obvious gotchas):

- **default bind is `0.0.0.0:1025`, override with `ATLAS_BIND`** (see `src/main.rs`).
  The in-repo `a.log` shows `1245` because that instance ran with `ATLAS_BIND`
  set — the port is not hardcoded; don't assume a port, read the env default.
- **net speed chain falls back cleanly with no root.** On non-root devices every
  level of the chain (su → sysfs → netlink → `/proc`) fails; `devsrc.rs` returns
  an empty snapshot and the dashboard shows idle rings — that is correct, not a
  bug. A `WARN "net speed source chain exhausted"` in the logs means the device
  has no su/sysfs/netlink access. See `src/v1/system/network/speed/devsrc.rs`.
- **battery 50/55 thresholds are high (industry avg 30/45).** Chosen by the user;
  the low/battery policy uses `atlas-batt` (low) + `atlas-batt-rearm` (rearm).
  Edit thresholds in `src/v1/operator/batterywatch.rs` if desired.
- **dashboard.html must stay a single self-contained file.** Compiled copy is
  embedded via `include_str!` in `web/mod.rs` (~133 KB), so edits to the **root**
  file require a rebuild (breaking the `include_str!` path or splitting the file
  breaks the runtime dashboard). For dev hot-reload without rebuild, drop a copy
  at `~/.local/share/atlas_prime/dashboard.html` — `h_dashboard()` reads it on
  every request and overrides the embedded binary. (see `src/v1/web/mod.rs`).
- **db rows are batched + trimmed per round.** `MAX_ROUNDS=20000` for non-net
  rows (≈ 27.7 d of 2-min sampling) and `NET_MAX_ROUNDS=28800` for net rows
  (≈ 8 h at 1 Hz); net and non-net are trimmed independently. Long write latency
  is by design for constrained Termux storage — don't "fix" it to synchronous
  per-row writes without re-evaluating the storage cost.
- **gpu card auto-hides when `available!=true` or absent** (frontend contract in
  dashboard.html); no alarm is raised. Seeded lazily on first `/system/gpu`.
- **/system/cli/network and /system/cli/battery are the only dashboard sources**
  for net and battery — battery comes straight from the termux-api CLI JSON (via
  `system/battery.rs`), not an internal collector path. If you add a new sensor,
  wire it through the 120s sampler loop so it lands in `db.records`.
- **single-instance lock via flock** on `~/.local/share/atlas_prime/atlas_prime.lock`
  (boot.log): concurrent launches exit cleanly — expected, not a crash.
- **release profile is size-tuned** (`opt-level=z`, lto, strip, panic=abort). Use
  `cargo build` (debug) for iteration; `--release` for deploy.
